# ADR-001 · 保持 Compose 原生，不整体复刻 WebView 形态

- 状态: 已采纳
- 日期: 2026-11-26
- 相关: `spec/parity/PARITY-NOTICE.md`、`spec/parity/PARITY-BASELINE.md`

## 背景

对标项目 B（`Buwrt/githup`）以「WebView 壳 + 4 万行手写 JS」承载全部界面，
并用 8,477 行的 `JsBridge.java` 暴露约 130 个原生能力。其功能广度显著高于 A，
但攻击面、可测试性、可访问性与性能均劣于原生实现。

## 决策

**A 保持 Compose 原生架构**，仅在「Markdown / 长文渲染」这类确有必要的场景允许内嵌渲染组件；
**不整体复刻 WebView 形态，不建立 JS 桥接面**。

对标方式为**清洁室复刻**：只复刻外部可观察行为，零代码 / 注释 / 文案 / 图标引入；
需要引码时改用许可兼容的第二参照（gh4a，Apache-2.0）并登记 `THIRD-PARTY.md`。

## 理由

1. **资产价值**：A 已有的 30 模块架构、236 单测、8 项质量门禁、Ktor/Room/Keystore 基线，
   价值远高于 B 的形态；B 的形态是其功能广度的**代价**而非优势。
2. **攻击面**：整体改 WebView 等于丢弃 A 的全部积累去复制 4 万行前端，
   并把「渲染层 XSS = 令牌泄露」「文件访问面」「包可见性」等整类风险重新引入。
3. **可验证性**：A 的行为可被单测与门禁机器校验；B 的行为校验依赖人工比对。

## 后果

- **正面**：安全基线更高、回归可机器拦截、UI 走 Compose 生态（无障碍、响应式、动态取色可原生实现）。
- **负面**：单个功能的实现成本高于写 JS；功能广度需按 D0–D3 分阶段追赶，
  追赶期必须靠「先实现高价值写能力」而非「先铺界面」来保证可用性。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 整体改 WebView | 见「理由」第 2、3 条 |
| 双轨共存（WebView 承载长尾功能） | 长期维护两套 UI 与两套状态管理；且会把令牌暴露面重新引入 |
| 直接复制 B 源码 | B 无 LICENSE，默认保留全部权利，复制即侵权 |
