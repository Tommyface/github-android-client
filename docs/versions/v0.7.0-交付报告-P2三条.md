## 二、M12 · 断点续传真实缺陷修复

**根因**：`OkHttpDownloader.performOnce` 把服务端 `Content-Range` 写成 `null` 传入 `RangeRequest.decide`，导致 206 响应恒被判 `RESTART`；而旧 RESTART 分支删掉 `.part` 后仍以旧偏移 `append` 写入，会产出缺头损坏文件。断点续传实际从未生效。

**修复**：
1. 解析 `response.header("Content-Range")` → `ContentRange.parse` → 传入决策；只有起点与已收字节一致才判 `APPEND` 续写。
2. RESTART/TRUNCATE_REWRITE 一律从头覆盖（删除 `.part` + `append=false`），杜绝错位拼接。
3. 跨镜像切换保留 `.part`，下一源按已收偏移续传；不兼容时由 `TRUNCATE_REWRITE` 从头覆盖。
4. 新增回归测试 `contentRangeParsingDrivesRealResume`（206 带/不带 Content-Range 的 APPEND/RESTART 分支）。

## 三、M10 · 星标趋势曲线

**端点语义核实**（P13 要求"实施前先 curl 实测"）：
- 实测 `GET /repos/{o}/{r}/stargazers/history` 匿名返回 HTTP 200，字段 `{week,total,days}`；
- 经 [star-history 官方博客原文](https://www.star-history.com/blog/new-github-star-history-api)核对：`total` 是**周增量（非累计）**，最新周在前，`days` 周日起，每页≤30 周，无需身份。
- 累计曲线由客户端 `StarHistory.fromWeekly()` 反转后逐周累加（负增量按 0，不倒退）。

**实现**：domain（StarHistory/StarWeekEntry 模型 + 累加纯函数）→ data（DTO+API，端点 `stargazers/history?per_page=30`，404 降级空趋势）→ presentation（ViewModel 状态 + Compose Canvas 折线自绘 + 页脚数据来源标注）。

**测试**：domain 累加/负值/空序列、data DTO→累计+端点路径+404 降级、presentation 投影纯函数（空/单点/单调/全零），共 8 项新增断言。

## 五、M13 · 兼容性评估（no-go 后置）

**结论依据**（详见 `M13-GraphQL聚合兼容性评估.md`）：
1. **凭证类型不可达**：`repo:data` 不依赖 `auth.domain`，拿不到 `AuthMethod`；`AuthTokenProvider` 只返回 token 串不暴露类型；`GitHubApiClient` 无 GraphQL 通道。降级需引入跨模块依赖调整。
2. **无法实测**：出口 IP 被 GitHub 限流、无有效 token，无法验证"fine-grained PAT 调 GraphQL 被拒"这一决定性问题；实测 GraphQL 对无效 token 返回 401 Bad credentials（端点可达但无有效凭证）。
3. **收益/成本比低**：stars/forks 已由单次 REST 返回，GraphQL 仅省 1–2 次 round-trip，却要引入 POST 通道+凭证贯穿+PAT 降级三套机制。

遵循 P13 原文"或直接后置"的出口，本轮不改产品代码，保持架构纯净。重启前置条件已在评估文档中列明。
